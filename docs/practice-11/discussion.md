# Discussion questions (Practice #11)

**Why should an LLM explain availability but not determine it?**
Availability is a yes/no rule: times, overlaps, blocked flag. A pure function decides it the same way every time, and the tests prove it. A model is probabilistic and can be steered by text, so it can be wrong in ways no test catches. In the prompt comparison, prompt B wrote "You're all set to go ahead with this booking", and prompt A invented reasons why a room might be blocked. Letting either of those decide would mean double bookings, or students turned away for no reason. The model is useful only for the part that is allowed to be fuzzy: wording. Even that is checked against the deterministic result before it is shown.

**How does an agentic reviewer differ from a linter?**
A linter applies fixed, local rules to syntax: unused variables, style, known-dangerous APIs. It gives the same answer every time and does not know what the feature is for. The agentic reviewer read the diff together with AGENTS.md, the feature contract and the tests, ran the test suite, and reasoned about behaviour across files. It found that the output validator would accept "You may reserve Room A-101" for an unavailable room (F2), that one test could never fail (F3), and that a cancel signal that was already aborted is ignored (F5). None of these is a syntax pattern, so a linter cannot express them. The cost is that its findings are hypotheses. Its line numbers pointed into the diff output rather than the files, and it marked F1 "confirmed" without having run the probe. So every finding had to be reproduced (see `agentic-review.md`).

**Which AI-generated finding would you refuse to accept without evidence?**
Any finding that claims a behaviour without a reproduction. The most dangerous kind is a security or correctness claim like "X allows prompt injection" or "this races", because accepting it leads to code changes. In this review I treated every finding as unverified until I had a failing test or a probe output (`evidence/p11/06-*`). All 9 findings reproduced. I kept the three hypotheses separate: H2 (real-model latency) is still unverified because I could not measure it properly. I would also refuse any "tests pass" claim that has no command output behind it.

**What should the application do when the model is unavailable?**
Exactly what it does now. Keep the deterministic decision on screen unchanged. Show a fixed, pre-written explanation for the reason code, labelled "Standard explanation · AI not used", with a short note on why (took too long / unavailable / failed safety checks). Never retry in a tight loop, never block the booking flow, and never show a raw error or stack trace. The feature is optional, so the app works fully without it.
